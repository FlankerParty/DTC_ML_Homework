**Homework 2 错误与经验总结**

# Q3：验证集使用自己的均值——预处理泄露

这次最重要的认识是：

> 模型不仅仅是最终求出来的权重 (w)，数据预处理过程中从训练数据学习到的参数也属于模型的一部分。

例如均值填充：

```
mean = df_train['horsepower'].mean()
```

这里的 `mean` 是从训练集估计出来的参数。

因此正确流程应该是：

```
mean = df_train['horsepower'].mean()X_train = prepare_X(df_train, mean)X_val = prepare_X(df_val, mean)X_test = prepare_X(df_test, mean)
```

而不能分别计算：

```
df_train.mean()df_val.mean()df_test.mean()
```

同样的原则也适用于：

- 均值、Median、Mode 填充

- StandardScaler 的 mean / std

- MinMaxScaler 的 min / max

- PCA

- 特征选择

- 从数据学习得到的编码规则

可以统一理解为：

```
fit(train)transform(train)transform(validation)transform(test)
```

而不是：

```
fit_transform(train)fit_transform(validation)   # 错误fit_transform(test)         # 错误
```

---

## 错误表现

原来的代码类似：

```
X = prepare_X(df_train, df_train.mean())
X_val = prepare_X(df_val, df_val.mean())
```

问题出现在：

```
df_val.mean()
```

虽然 validation 没有参与线性回归权重：

```
w = (X.T @ X)^-1 @ X.T @ y
```

的计算，但 validation 的整体分布已经参与了自己的预处理。

这属于：

```
Data Leakage└── Preprocessing Leakage
```

## 为什么算数据泄露

正常验证流程应该模拟模型上线后的场景。

模型训练完成后：

```
训练数据    ↓计算 horsepower_mean    ↓训练模型    ↓冻结 mean 和模型权重    ↓未来新数据
```

未来数据到来时，例如：

```
horsepower = NaN
```

应该使用历史训练数据得到的均值填充，而不是先观察未来数据整体分布，再重新计算一个均值。

Validation 的作用之一就是模拟这种“未来未知数据”。

因此 validation 不能参与：

```
均值标准差最大值最小值PCA特征筛选
```

等参数的估计。

---

## 为什么会影响模型评估

验证误差的目标是估计模型面对真正未知数据时的泛化性能。

理想情况下：

[  
\hat f = A(D_{train})  
]

即模型完全由训练集决定。

然后使用独立验证集：

[  
D_{val}  
]

计算：

\frac{1}{n}  
\sum_i  
L(\hat f(X_i), Y_i)  
]

从而估计真实泛化风险：

E[L(\hat f(X),Y)]  
]

关键前提是：

[  
\hat f  
]

在看到 validation 之前已经确定。

如果使用：

\frac{1}{n}\sum_i X_i  
]

处理 validation，那么预测实际上变成：

f(X_i;\mu_{val})  
]

而：

g(X_1,\dots,X_n)  
]

所以一个 validation 样本的处理已经依赖整个 validation set。

此时评估的不再是：

> 固定模型面对未知样本时的表现

而变成：

> 模型提前知道未来这一批数据整体分布以后表现如何

因此可能产生 optimistic bias，即验证结果过于乐观。

---

## 为什么这次数值变化可能不明显

这次 Q3 中：

- 只有 `horsepower` 存在缺失值

- 缺失数据数量有限

- train mean 和 validation mean 可能比较接近

因此数据泄露对最终 RMSE 的影响可能非常小。

这说明：

> 数据泄露是否存在，不能通过“结果差异大不大”判断。

即使最终：

```
With mean
```

这个答案没有变化，方法仍然是不正确的。

应该从实验设计本身判断是否存在 leakage。

## 配套经验：fillna 传 Series 的行为

如果：

```
mean = df_train[base].mean()
```

返回：

```
engine_displacement    ...horsepower             ...vehicle_weight         ...model_year             ...dtype: float64
```

那么：

```
df.fillna(mean)
```

会根据 Series 的 index 和 DataFrame 的列名进行匹配。

例如：

```
df.fillna(    pd.Series({        'horsepower': 250,        'vehicle_weight': 3000    }))
```

等价于：

```
horsepower 的 NaN      → 250vehicle_weight 的 NaN  → 3000
```

因此多列存在缺失值时，可以直接：

```
mean = df_train[base].mean()X_train = prepare_X(df_train, mean)X_val = prepare_X(df_val, mean)
```

不需要逐列填写。

# Q4：没有按照题目要求保留四位小数

原来的输出：

```
round(RMSE, 3)
```

但题目要求：

```
round(RMSE, 4)
```

这次不同 `r` 的结果差别比较明显，所以最终：

```
r = 0
```

没有受到影响。

但这是一个值得注意的问题：

> 题目规定的 rounding precision 本身可能影响选项判断。

例如：

```
2.205242.20531
```

保留三位：

```
2.2052.205
```

看起来相同。

保留四位：

```
2.20522.2053
```

实际上存在差异。

因此做机器学习作业时，题目指定：

```
round(..., 3)round(..., 4)
```

不能当成单纯的输出格式要求。

# Q5：每个 seed 都必须重新切分

Q5 的正确流程是：

```
for seed in seeds:    np.random.seed(seed)    idx = np.arange(n)    np.random.shuffle(idx)    df_train = ...    df_val = ...    df_test = ...    train model    evaluate validation
```

不能只：

```
np.random.seed(seed)
```

然后继续使用之前已经切好的数据。

因为这个实验真正研究的是：

> Train / Validation 数据划分的随机性会对模型性能产生多大影响。

因此每个 seed 都必须产生新的 split。

最终：

```
np.std(RMSEs)
```

衡量的是不同数据划分下模型性能的波动。

这可以粗略反映模型对数据划分的稳定程度。

# Q6：没有合并 Train 和 Validation

Q6 要求：

```
seed = 9train 60%validation 20%test 20%train + validation        ↓     重新训练        ↓      test
```

但原来的实现实际上还是：

```
X = prepare_X(df_train, 0)y_train = df_train['fuel_efficiency_mpg']
```

`df_val` 没有参与最终训练。

正确做法：

```
df_full_train = pd.concat([df_train, df_val])X_full_train = prepare_X(df_full_train, 0)y_full_train = df_full_train['fuel_efficiency_mpg']w0, w = train_linear_regression_reg(    X_full_train,    y_full_train,    r=0.001)X_test = prepare_X(df_test, 0)y_pred = w0 + X_test.dot(w)
```

## 为什么最终要把 Train 和 Validation 合并

在模型开发阶段：

```
train↓训练参数validation↓选择模型 / 超参数
```

当超参数已经确定，例如：

```
r = 0.001
```

validation 的模型选择任务已经完成。

此时 validation 不需要继续保留，可以将：

```
train + validation
```

合并，利用更多数据重新训练最终模型。

然后：

```
test
```

只使用一次，用于最终性能评估。

因此三个数据集的职责是：

```
Train    学习模型参数Validation    选择模型和超参数Test    最终独立评估
```

模型选择完成以后：

```
Train + Validation        ↓   Final Model        ↓       Test
```

---

## 配套经验：Train、Validation、Test 的职责不能混淆

```
Train       → 学参数Validation  → 选模型Test        → 最终评估
```

确定模型以后：

```
Train + Validation → Final TrainingTest               → Final Evaluation
```

# 通用经验：不能只检查最终答案

Q6 原来的错误实现依然得到了：

```
2.236
```

而这个值刚好是正确选项。

这是这次作业一个很重要的经验：

> 最终数字正确，不代表实验流程正确。

可能出现：

```
错误实现   ↓数值恰好接近   ↓选择了正确答案
```

但换一个数据集之后，同样的错误可能直接导致完全不同的结论。

机器学习代码需要同时检查：

```
实验设计数据流计算逻辑最终数值
```

而不能只验证最终答案。

---

## 机器学习作业的检查重点

应该同时检查：

```
题目要求↓数据划分↓预处理↓训练↓验证↓最终训练↓测试
```

只要其中一步的数据边界错误，即使最终数字碰巧正确，实现依然有问题。

---

# Train / Validation / Test 的信息边界

以后可以始终按照下面的原则判断是否存在数据泄露。

### Train 可以做什么

可以：

```
计算 mean计算 std训练 scaler训练 encoder做 PCA选择特征拟合模型参数
```

因为这些东西本来就是训练过程。

### Validation 可以做什么

可以：

```
计算预测结果计算 RMSE比较不同模型比较不同超参数
```

不能：

```
反过来参与训练预处理参数
```

例如：

```
df_val.mean()
```

然后拿来处理 validation 自己。

### Test 可以做什么

原则上只应该：

```
使用最终确定的 pipeline↓预测↓计算最终指标
```

不能再根据 test：

```
修改特征修改超参数修改填充值修改模型结构
```

否则 test 就逐渐退化成另一个 validation set。
